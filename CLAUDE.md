# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

"Burrec mos u zemero" — a 3D Ludo-style board game (Albanian take on "Mensch ärgere dich nicht"). Vue 3 + Three.js for rendering, cannon-es for dice physics, nes.css for retro UI. Playable on desktop and mobile/touch: the old `.mobile-block-overlay` is disabled (`display:none`), and on touch (`store.isMobile`) the HUD shows an explicit Roll button since tapping the small 3D dice-in-pit is fiddly on a phone. No tests or linter are configured.

Production is `burrec.com`, served from a DigitalOcean droplet (Caddy TLS + reverse proxy to Nakama; see `nakama/DEPLOY.md`) — `docs/` also still gets committed and can serve as a GitHub Pages mirror, which is why `vite.config.js` uses a relative `base: './'` rather than a repo-path base. `.github/workflows/deploy.yml` deploys automatically on every push to `master` (or manual dispatch): always rebuilds and rsyncs the client, and only rebuilds/ships the Nakama bundle + restarts the server stack when server-relevant files changed (restarting drops all live matches). `docs/ROADMAP.md` (planned features) lives in that folder — `pnpm build` cleans `docs/` before writing, so anything not tracked in git there gets silently deleted on the next build. `.env.production` (Nakama host/key) is committed and baked into the build at build time.

## Architecture

Three layers communicate through a shared reactive singleton and an event bus — there is no Pinia/Vuex in the live path.

**State: `utils/ApplicationStore.js`** — a plain Vue `reactive()` object imported directly by everything. Holds board geometry (`fields.home/target/path` as THREE.Vector3 grid coordinates), `players`, turn bookkeeping (`currentPlayerId`, `currentRound`, `lastRolledDice`), UI screen (`currentScreen`: `main-menu` → `create-room`/`join-room` → `lobby` → `game-screen`; the app is online-only), graphics `settings`, and `gamePlayStatus.isRolling/isMoving` which gate all interaction.

**Game rules: `utils/Player.js` and `utils/Pawn.js`** — plain classes that mutate ApplicationStore directly. `Player` owns turn flow after a dice result (three-roll rule when all pawns are home, six repeats the turn, computer players auto-roll/auto-move on timeouts). `Pawn` owns movement: it builds a list of step states and applies them on `PAWN_STEP_DURATION_MS` timers (`runMoveSequence`), then handles captures (`removeOpponentPawns`) and fires the end/repeat-turn event. Position model: `position` 0 = home, 1–40 = main path (`globalPosition = (startingGlobalPosition + position - 1) % 40`, players start at offsets 0/10/20/30), 41–44 = the player's target lane; moves that would overshoot ≥ 45 are unavailable.

**Rendering + orchestration: `App.vue` (~2100 lines, deliberately monolithic)** — owns the Three.js scene, the cannon-es physics world, and the game-flow handlers (`startGame`, `changePlayersTurn`, `repeatPlayersTurn`, `rollDice`). Key subsystems:

- *Scenery*: the meadow, table and sun are procedural; everything else (mountains, hills, trees, bushes, rocks, grass, reeds, clouds) is the CC0 Gobkit Nature Kit (`src/assets/nature/*.glb`, cm units, one shared palette texture). `utils/natureKit.js` loads them and holds the placement tables; `createNatureEnvironment` bakes the placements asynchronously after the board into static merged meshes (backdrop: palette + clouds; details: 1). Rocks/grass/reeds are the `decorationMeshes` (hidden on the lowest quality preset). Only the models the tables reference are shipped — copy more from the kit zip if needed.
- *Toon look*: every mesh gets an inverted-hull outline shell (`attachOutlineShell` / `createOutlinedInstancedSet`, `userData.isOutlineShell`). Geometries, materials, and textures are cached in `sharedGeometries/Materials/Textures` via `getShared*` — reuse those helpers instead of constructing Three objects inline. Keep the draw-call count low: all board field discs are one `createOutlinedInstancedSet` (per-instance scale/color/outline), a pawn is one merged body+head geometry with a pre-baked outline shell (`buildPawnGeometry`), the dice is one material over a 3x2 pip atlas (`buildDiceGeometry`). Lighting is 3 lights (hemisphere carries the ambient term, `ENVIRONMENT_LIGHTING` table) — avoid adding lights, they're per-fragment cost everywhere.
- *Dice*: physics-based. `startDiceRoll` throws the body with a random impulse inside a walled tray; `stepPhysicsWorld` watches for settling, detects the up face by dotting face normals with world-up, nudges tilted dice (max 3 recovery attempts), then snaps face-up and calls `completeDiceRoll` → `Player.rollDice`.
- *Pawn animation is one-way*: game logic changes `Pawn` state instantly (per-step timers); the render loop's `syncPawns` reads `pawn.getCoordinates()` each frame and tweens meshes toward it, keyed on a logical position string (`getPawnWorldState().key`).
- *Interaction*: raycasting only targets objects valid for the current phase (`getInteractiveHit` checks `isRolling`/`isMoving` + `isHumanTurn`). Highlights are not 3D — a 2D overlay canvas projects constant local-space outline points (module-level `PAWN_BODY/HEAD_LOCAL_POINTS`, `DICE_LOCAL_CORNERS`) to screen space through a scratch vector, takes the convex hull, and strokes it (`renderHighlights2D`).
- *Demand rendering*: the rAF loop always runs the simulation, but `renderer.render` only fires when something changed — continuous sources (menu orbit, camera flight, dice physics awake, hit effects, Finisher) are enumerated in `needsContinuousRender()`; every discrete visual change must call `requestRender()` (or `requestShadowUpdate()`, which implies it) or it won't appear. **All rendering is capped** — target 48fps on desktops/laptops, 24fps on phones/tablets, on battery (Battery API, Chromium only) or when auto quality finds the high cap unsustainable (`updateRenderCap`). The real cap is every Nth vsync of the measured refresh rate (`sampleRefreshRate`/`refreshDivisor`, ties toward smoother): 60Hz → 60/30, 120Hz → 60/24, 144Hz → 48/24 — an uneven cadence like 24 on 60Hz judders, so never go back to fractional phase-locking; the dirty flag survives capped frames so final states still draw. Clickable cues (ground rings, hover outline, lobby chips) are deliberately static — an animated cue forces continuous rendering for a whole turn, so don't reintroduce pulses. Per-frame loop bookkeeping (`renderNeeded`, `hoveredTarget`, …) lives in `created()`, outside reactive `data()`. HUD animations must stay transform/opacity-only (the turn-timer bar is a pure CSS `scaleX` drain). `sampleRenderPerformance` watches consecutive rendered-frame deltas and first drops the high cap to the low one, then steps `settings.quality` down (never up, max twice) on slow devices — the manual quality UI was removed.

**Events: `utils/eventhandler.js` + `utils/EventKeys.js`** — a tiny EventTarget wrapper. UI components fire `game.start` / `game.rollDice`; Pawn/Player fire `turns.endTurn` / `turns.repeatTurn`; App.vue subscribes in `addEventListeners`. Add new keys to `EventKeys.js`, never string literals.

**Vue reactivity discipline**: all Three.js/cannon-es objects are wrapped in `markRaw()` before being stored on component data or in ApplicationStore (see the `vector()` helper in ApplicationStore). Keeping them out of Vue's proxy system is essential for performance — follow this for any new scene objects.

**Graphics settings** (`utils/outlineAppearance.js`, `utils/renderQuality.js`) are preset tables; App.vue watchers on `store.settings.*` re-apply them live (`applyOutlineAppearance`, `applyRenderQuality`).

The app is online-only (server-authoritative Nakama matches); the offline "Local Game" mode and its `add-players`/`localSetup*` setup were removed. Opponents nobody takes are server-side Bots (see Online multiplayer); `Player.controller === 'ai'` is a leftover local-AI path, unused online.

## Online multiplayer (Nakama)

Online games are **server-authoritative**: a Nakama TypeScript runtime module (`nakama/`, bundled by rollup to ES5 for goja) owns dice RNG, move validation, captures, turn order and win detection. The client replays server events through the existing animation path.

- **Protocol**: `shared/protocol.js` defines the opcodes and is imported by both sides — never let client and server drift; extend this file only.
- **Server**: `nakama/src/ludo_logic.ts` is a pure, node-testable port of `Pawn.js` rules (keep them in exact parity — door blocking, own-pawn collisions via seat-relative `position`, overshoot ≥ 45, captures only on the main track). `match_handler.ts` runs lobby → playing → finished; **all timing lives in matchLoop ticks** (tick rate 2, goja has no setTimeout): turn timeouts (60s, 6s for disconnected), Bot pacing, empty-match termination (60s). Private lobbies use 5-char codes resolved purely via match-label queries (`+label.code:X +label.open:1`) — note the label index lags `matchCreate` by ~1s (client retries once).
- **Client bridge**: `src/network/MatchController.js` maps opcodes ↔ EventBus/ApplicationStore. MOVE_APPLIED/TURN_CHANGE/GAME_OVER go through a FIFO that pauses while dice physics (`store.online.diceInFlight`) or a pawn animation (`pawn.moveComplete` event) is in flight.
- **Player.controller**: `'local' | 'ai' | 'remote'` replaces the old isComputer boolean (getter kept). All interactivity checks use `controller === 'local'`.
- **Dice online**: the physical roll is cosmetic. `App.rollDice` starts physics immediately (latency hiding); `finishDiceSettle` never feeds the physical face to game logic online — `tryResolveOnlineDice` waits for the server value, `snapDiceToValue` tweens the correct face up, then `completeDiceRoll(serverValue)` runs the presentation-only `Player.applyServerDiceResult`.
- **Turns online**: `Pawn.endOfMove` fires only `pawn.moveComplete`; turn flow comes exclusively from TURN_CHANGE → `App.setTurnBySeat` (seats can be non-contiguous — never use `changePlayersTurn`'s array rotation online; `store.online.seatToPlayerIndex` maps seat → players index, while `Player.turn - 1` stays the seat for colors/board offsets).
- **Recovery**: any REJECTED or desync path sends SYNC_REQUEST; `handleNetStateSync` rebuilds players and teleports pawns from the snapshot.
- **Bots** (terms in `CONTEXT.md`: Bot, Abandoned seat): every seat no human holds is a Bot from `matchInit` on (`bot: true`, `userId ''`, shown as "Computer" via `seatPlayerName`), so the host can START as soon as they're seated — no player-count or ready checks. Claiming a seat replaces its Bot; unclaiming/leaving in the lobby hands it back. Bots are played in `matchLoop` by `playBot` on `state.botActTick`, which `holdBots` pushes past the client's dice/move/capture animation time (`BOT_*` constants, keep roughly in sync with `PAWN_STEP_DURATION_MS` and Finisher lengths). Their pick is `chooseBotMove` in `ludo_logic.ts` — also the Abandoned-seat timeout autopilot. Bots wear `guestCosmetics()` (lite Capture), aren't chat/Report targets, and are left out of per-player stats. Client-side they're `controller: 'remote'` (never `'ai'`, which auto-plays locally); DICE_RESULT joins MatchController's FIFO when anything is still animating, since Bots roll on the server's clock.
- **Drop-in joins**: `label.open:1` means "a seat is claimable" — a lobby or running game with a Bot or an Abandoned seat. Mid-game joiners arrive unseated (server sends them a STATE_SYNC; client shows the choose-color banner), then CLAIM_SEAT during `playing` takes over a Bot or a disconnected seat with its pawns as they stand; the server broadcasts STATE_SYNC to everyone so clients rebuild rosters. Disconnected seats' pawns are dimmed client-side (`applySeatPresence`, per-seat shared materials at 0.35 opacity).
- **Per-game environment**: the room creator's `settings.environment` rides the create RPCs into matchInit params, is broadcast in LOBBY_STATE/STATE_SYNC, and lands in `store.online.environment`, which overrides the local setting while in a match. `state.displayNames` (userId → name, seated or not) travels the same payloads so chat can name unseated players.
- **Cosmetics** (terms in `CONTEXT.md`): a Prop (+ the country `flag` the flag Prop waves) **per pawn**, and one Finisher per player. Shape (`sanitizeCosmetics`): `{ finisher, pawns: [{prop, flag} x4], prop, flag }` — top-level prop/flag mirror pawn 0 for older clients; `pawns` rides join metadata as a JSON string (Nakama metadata is string-valued); render via `pawnLook(cosmetics, startingPlace - 1)`. The Wardrobe has an All / 1–4 pawn selector (`store.wardrobe.previewPawn` picks which pawn the preview wears). Ids/whitelists live in `shared/protocol.js` (`sanitizeCosmetics`, `FLAG_CODES`; flag SVGs are vendored from flag-icons into `public/flags/`). They are edited **only** in the Wardrobe (`WardrobeScreen.vue`: the menu screen `currentScreen: 'wardrobe'`, or the in-game overlay below): it edits `store.wardrobe.draft`, Save commits to `settings.cosmetics` + localStorage. Cosmetics ride join metadata; once the game runs, a seated Member gets **one** restyle per match: the HUD's Style button opens the same Wardrobe as an overlay (`store.wardrobe.inGame`, currentScreen stays `game-screen`; App.vue's `wardrobeOpen()` covers both), "Wear it" sends `SET_COSMETICS`, and the server answers `COSMETICS_CHANGED` to everyone or REJECTED `restyle_used`/`members_only` (`state.restyled`, also in STATE_SYNC). For a Guest the Style button is the register pitch (`promptRegister('restyle')`) — linking keeps the user id, so they can register and restyle without leaving the match. A Wardrobe-preview Finisher never touches `finisherInFlight`/`finisher.done`, and never preempts a real capture's Finisher. A rejoiner keeps their stored Cosmetics. Stored per userId, broadcast as `cosmetics` in LOBBY_STATE/STATE_SYNC; MOVE_APPLIED stamps the mover's `finisher`. Prop meshes and the picker catalog are in `utils/cosmetics.js`; The close-up camera (`poseFinisherCamera`) arcs around the action in spherical coordinates (never a straight dolly), leads with the look, backs off by the viewport's horizontal FOV so attacker + victim fit portrait phones, drifts slowly during the hold and follows a third of the victim's flight home — all on module scratch objects. Finisher tools, the per-Finisher timeline (`finisherTiming`, hit-stop via `actionTime`) and every pose function (tool, attacker, victim, Prop wobble, landing dust) are pure functions of time in `utils/finishers.js`, which App.vue's `startFinisher`/`updateFinisher`/`endFinisher` run (one tool stage per victim, mirrored so tools face the close-up camera; the trapdoor's pit is a stencil cutout through the board, which is why the renderer is created with `stencil: true`). Transforming Finishers (magic wand → rabbit, vampire → bats, UFO) swap or hide the victim between impact and touchdown (`victimForm`); tools that travel to the victim's home get it in their stage frame (`tool.userData.home`). Props hang off a head-center pivot (`tiltProp`) that only moves during a Finisher; face Props sit on the pawn's local +Z, and board pawns are yawed toward the camera (`pawnFacingYaw`) so faces are always seen. The Wardrobe preview is a separate little scene (`ensureWardrobeStage`) that the main renderer draws scissored into the panel rect `store.wardrobe.rect` after the board, so props/Finishers preview through the same code (`startWardrobeFinisher`). The capturing hop lands *beside* the victim (`Pawn.landingOnCapture` → `captureLandingOffset`, Finishers on only); the victim is hit on its own square and the attacker hops onto it once the victim is sent home. A Capture stays logically instant — only the victims' meshes are held (syncPawns skips `finisher.victimIds`), and `store.online.finisherInFlight` pauses MatchController's queue until `finisher.done`. Tap skips; `settings.finishersEnabled` off (a viewer preference in Settings) = "lite" (no zoom/tool, just burst + flight home).
- **Admin stats**: `stats.ts` keeps one system-owned storage object (games started/finished, per-player counts, last 50 games), written from match start/game-over; surfaced by `admin_overview`. Client dashboard at `#admin` (AdminScreen.vue: Reports / Users / Stats tabs + user detail).
- **Moderation** (`moderation.ts`, terms in `CONTEXT.md`): Admins = Members whose id is in the `ADMIN_USER_IDS` runtime env (the refused #admin screen shows the caller's id); every `admin_*` RPC re-checks. Block = user-owned `blocks/list` (RPC-only), filtered client-side in `ChatController.handleMessage` + `ChatDrawer.visibleMessages`. Report (`report_player`, Guests too, rate-limited, one open per reporter→target pair, also Blocks): chat evidence is copied from the server's own channel history — that's why match chat channels are joined **persistent** — falling back to the reporter's text flagged unverified. Shadowban: the `ChannelMessageSend` rt-before hook **throws** (never return null from an rt-before hook: Nakama then closes the sender's socket, dropping them from their match); the sender doesn't notice because `ChatController.send` echoes own messages optimistically and swallows send errors. Ban = Nakama `usersBanId` (cuts live sockets, refuses sign-in). Admin actions append to `user_meta` history. The daily Report digest email runs from a never-written leaderboard's reset schedule (`report_digest_clock`, 08:00 UTC) — goja has no timers, and the reset hook fires even with no records. `PlayerActions.vue` (Block/Report sheet) opens from a tapped chat message or another player's seat chip via `openPlayerActions` (`utils/authPrompt.js`).
- **Dev identity**: deviceId lives in sessionStorage in dev (per-tab, so two tabs can play each other) and localStorage in prod.
- Session tokens: `token_expiry_sec` is raised to 7200 in `local.yml` (Nakama's 60s default kills sockets mid-game).
- **Accounts** (optional — guest device auth stays the default): email register/login plus Google/Apple sign-in (`AuthModal.vue`, buttons config-gated on `VITE_GOOGLE_CLIENT_ID`/`VITE_APPLE_CLIENT_ID`; Apple also needs `social.apple.bundle_id` server-side). Nakama sends no email itself: `nakama/src/auth.ts` mints one-time tokens in system-owned storage and posts to Resend's HTTP API (`runtime.env`: RESEND_API_KEY, EMAIL_FROM, PUBLIC_URL; EMAIL_DEV_ECHO=1 in dev returns the links in RPC payloads). Verify/reset links land as `#verify=`/`#reset=` hashes handled by StartScreen. The email HTML (`emailHtml` in `auth.ts`) mirrors the game UI — orange panel, dark-green border, pill title, green chunky button — in tables + inline styles (no inset shadows or negative margins; mail clients drop them). Password reset works via `nk.linkEmail` re-link; the reset/verify RPCs run under any session (guests included) and act on the token's user, never the caller. An expired non-guest session throws `auth_session_expired` instead of silently re-authenticating as a guest device.
- **Guest vs Member** (terms in `CONTEXT.md`): a Member has a Google/Apple login or a *verified* email; everyone else (device-only, or email not yet verified) is a Guest. Registering **links** the login onto the Guest's own Nakama user (`linkEmail/linkGoogle/linkApple`, adr/0001) so the user id carries over; a Google/Apple login already owned by another user (409) falls back to signing in to it. Because the device id then authenticates as the Member, `NakamaClient.logout()` rotates the device id. Server-side gates use `isMember` (`auth.ts`): Guests get `guestCosmetics()` (no Prop, `NO_FINISHER` → lite capture) at join/`SET_COSMETICS`, and a `ChannelMessageSend` rt-before hook rejects their chat. Client mirrors it via `store.online.account.member` (Wardrobe banner + "Register to save", locked chat field) and `utils/authPrompt.js` opens the modal with a reason. `delete_account` RPC handles App Store 5.1.1(v).
- **Store** (terms in `CONTEXT.md`: Price tier, Entitlement, Claim): `ITEM_TIERS` in `shared/protocol.js` is the whole catalog config — items not listed are free; `{ tier: 'special', from, until }` (UTC dates, `until` exclusive) is Claimable by Members in-window via `claim_item`; `{ tier: 'premium' }` only via an Entitlement (no purchase flow yet). Entitlements are user-owned storage (`entitlements/items`, server-write-only; account deletion removes them). The server enforces `wearableCosmetics(…, ownedItems)` at join/`SET_COSMETICS`; the client mirrors it (own seat in `cosmeticsForSeat`, Wardrobe badges + Claim note, Save disabled for unowned picks) using `store_state`'s server clock. Adding a holiday special = one `ITEM_TIERS` line + a server deploy.
- **Start screen + corner buttons** (StartScreen.vue): non-Members see two panels — "Play now" (name + Play as guest) and "Register" (`AuthProviders`: Apple first per guideline 4.8, Google's own rendered button, email). Email swaps both panels for `AuthModal` rendered `inline` (own local view, emits `close`). Menu screens pin Settings + Profile top right (`.menu-corner`); the Profile button carries the sign-in provider's mark (orange = email not verified). `ProfileSheet` holds name, Wardrobe, linked account, sign out, delete; Settings holds language/sound/finishers, the blocked-players list (guideline 1.2 findability; `block_list` returns names) and legal links. Cookie banner (`CookieConsent`, `utils/consent.js`) drives Google Consent Mode v2 — `index.html` defaults `analytics_storage` to denied unless `burrec.cookieConsent` is `accepted`.
- **Apple identifiers**: App ID / iOS bundle `com.afronorana.burrecmosuzemero` (Sign in with Apple enabled, primary); web Services ID `com.afronorana.burrecmosuzemero.web` (domain `burrec.com`, return URL `https://burrec.com/`; Apple rejects localhost, so Apple sign-in is only testable on prod). The Services ID is `VITE_APPLE_CLIENT_ID` and the droplet's `APPLE_BUNDLE_ID` (→ `social.apple.bundle_id`). **Native iOS caveat:** Nakama validates an Apple token's `aud` against that ONE id — web tokens carry the Services ID, native Sign in with Apple tokens carry the bundle id. When the Capacitor app ships, either use the web popup flow in-app (keeps the Services ID; simplest) or replace Nakama's check with a custom one that accepts both auds. No .p8 key / Team ID is needed for the current token-only flow. ADRs live in root `adr/`, never `docs/` (the build wipes it).
